02 — 你看到的发件人 ≠ 真正投递者

把邮件拆成两层

上层是给人看的信头；下层是邮件服务器用来追踪和验明身份的物流单。

用户看到
FromGold House North
GoldHouseNorthParcelNotice@gmail.com
Toallison@example.com
Reply-ToGoldHouseNorthParcelNotice@gmail.com
Subject您的包裹已到前台

“From” 是信封正面印给人看的署名，并不能单独证明是谁寄的。

邮件系统还看到

默认收起，避免一上来被术语淹没。

Envelope Frombounce@mail.msgsndrhq.com
DKIMd=mail.msgsndrhq.com; s=mailer1
发送 IP203.0.113.42
Message-ID<abc123@mail.msgsndrhq.com>
HELOoutbound.msgsndrhq.com

服务器会同时看“谁自称发件人”和“实际由谁投递、谁签名”。两套身份可以不同，但安全策略会检查它们是否合理地对应。

  • 用 Google 官方系统正常发信
  • gmail.com 的 DNS 配置
  • 替第三方服务器授权代表 gmail.com 发信
Google 控制
  • gmail.com 域名
  • gmail.com 的公开 DNS 记录
  • SPF 授权范围
  • DKIM 密钥与 DMARC 政策
拥有邮箱账号
像租到 1208 室≠拥有整个域名

04–06 — 三道身份检查

先授权，再盖章，最后对名字

按顺序认识 SPF、DKIM、DMARC。点击术语可看原因，而不只是 PASS / FAIL。

1 · 授权名单

SPF

“这个域名允许哪些服务器替它投递？”

mybuilding.com 的 DNS
  • Google Workspace
  • thirdparty-mail.com

第三方在名单里 → SPF PASS

为什么 gmail.com 不行？

你无法修改 Google 管理的 gmail.com 授权名单，所以不能把任意第三方加进去。技术上，SPF 验证的通常是 Envelope From / Return-Path 域名与发送 IP，而不是人看到的 From。

2 · 防拆封印

DKIM

“邮件确由签名域发出，途中关键内容没被改。”

发送方用私钥盖章→收件方去 DNS 找公钥验章

签名 d=mybuilding.com → 身份是 mybuilding.com

了解一点密码学

私钥只在发送方，负责生成不可伪造的摘要签名；DNS 里的公钥让任何收件服务器验证，却不能用来伪造签名。selector（如 s=mailer1）告诉服务器去 DNS 的哪个位置找公钥。

3 · 对齐裁判

DMARC

“人看到的 From 域名，是否与至少一种通过认证的身份对得上？”

可见 From：mybuilding.com

DKIM d=：mybuilding.com

域名对齐 + DKIM 通过 → DMARC PASS

DMARC 还做什么？

域名所有者可在 DNS 公布策略（如监控、隔离、拒绝）并接收汇总报告。DMARC 不要求 SPF 与 DKIM 都对齐；通常任一“通过且对齐”即可。

07 — Alignment / 域名对齐

三个名字，至少有一个可信证件要对上

把可见 From 想成口头自我介绍，SPF / DKIM 像物流工牌和公司防伪章。

09–10 — 为什么 Gmail 特别麻烦？为什么会改写？

发送商把一个无法证明的身份，换成自己能证明的身份

客户想显示
GoldHouseNorthParcelNotice@gmail.com
→
发送商无法控制
gmail.com 的认证
→
改写为可认证域名
…@mail.msgsndrhq.com
@
点地址的两部分拆解。注意：电子邮件地址按最后的 @ 分割。

改写不是“把 +gmail.com 变成新域名”。真正的域名是最后一个 @ 后面的 mail.msgsndrhq.com；前面整段只是这个域名下的邮箱名（local part）。服务商因此可以为自己的域名配置 SPF、DKIM、DMARC。

“发送成功”可能只完成了第一棒

→

250 accepted 仍不等于 Inbox：收件系统随后可能放入垃圾邮件、隔离区，或由用户/企业规则静默过滤。Deliverability（送达表现）关心邮件能否稳定抵达目标位置，尤其是收件箱；不只是程序调用没报错。

进入 Gmail / Outlook 的邮件室

拖动四组信号。认证是身份证，不是 VIP 通行证；通过认证也可能进垃圾邮件。

INBOX

认证清楚，整体信誉与行为信号健康。

这是教学模型，不是 Gmail 的真实评分公式。
小补课 — DNS 是什么？

域名放在互联网上的“公开配置栏”

拥有域名控制权，就能在这里公布谁可代发、验章公钥和处理政策。

mybuilding.com
├── 网站记录　→ 网站在哪里
├── MX 记录　 → 谁接收这个域名的邮件
├── SPF / TXT → 哪些服务器可以代发
├── DKIM　　　→ 用于验签的公钥
└── DMARC　　 → 对不合格邮件采取什么政策

DNS TXT 记录只是可发布文本的一种记录类型；SPF、DKIM 公钥和 DMARC 政策通常借它发布。服务商会提供要添加的具体值，客户在域名注册商或 DNS 平台粘贴并等待验证。

12 — SaaS 推荐架构

从脆弱冒充，到可验证的专业发信

脆弱 / 不推荐

直接冒充客户 Gmail

From
parcel@gmail.com

via third-party provider

平台无法替客户控制 gmail.com 身份；认证对齐容易失败，也可能触发改写或拒绝。

更好 / 低门槛

平台域名发信，回复给客户

From
notifications@saas.com

Reply-To
parcel@gmail.com

平台完全认证 saas.com。收件人按“回复”时，邮件仍发给客户 Gmail。

最佳 / 专业

验证客户域名或子域名

From
parcel@mail.mybuilding.com

DKIM d=mail.mybuilding.com

客户添加服务商提供的 DNS 记录。服务商用已验证的客户身份签名，品牌与认证对齐。

上线清单（概念级）
  1. 优先把平台自有域名作为安全默认 From，并单独设置 Reply-To。
  2. 为专业客户提供自定义发送域名 / 子域名验证向导。
  3. 让发送服务商给出 SPF 或 Return-Path 配置、DKIM 公钥记录、验证状态。
  4. 逐步启用 DMARC：先监控报告，再视情况 quarantine / reject。
  5. 处理退信、投诉、退订、速率与信誉；不要只看 API 200。

如果只带走一个心智模型

邮箱账号是房间；域名是整栋楼和门卫规则。

第三方发信时，收件系统不仅看邮件上写了谁，还看实际投递者、授权名单、防伪签名，以及这些身份是否与可见 From 对齐。可靠方案是使用平台已认证域名，或验证客户自有域名；客户的 Gmail 地址适合放在 Reply-To，而不是让陌生服务器冒充 gmail.com。
